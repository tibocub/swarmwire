## Phase 4: User Story 2 - Measuring how strategies behave in a large swarm (Priority: P2)

**Goal**: `npm run bench:sim` prints a reproducible comparison table for a large swarm.

**Independent test**: `npm run test:unit` with `sim.test.js` passing; `npm run bench:sim` run twice prints identical output; `-- --peers 1000` finishes in under ten minutes.

- [X] T011 [P] [US2] Write `test/unit/sim.test.js` first. The simulation's entry is a function `simulate(settings)` exported from `bench/sim/model.js`, returning `{ rows }` (settings and strategies are defined in T012 to T014). Tests on a small swarm (40 downloaders, 1 seeder, 64 groups, 16 neighbours, seed 1): (a) same settings and seed twice give deeply equal results; a different seed gives a different result. (b) For every strategy and every downloader, at the end it holds every group "exactly once" and the model counted each duplicate arrival as discarded (a duplicate never raises `have`). (c) Changing one setting changes only that: `uplink` doubled makes the last finisher no slower, and the graph (neighbour lists) is identical between the two runs. (d) A swarm of more peers than a hard cap (`peers > 20000`) throws a clear error before running ("rather than running for hours" edge case). (e) A swarm where a downloader cannot reach any seeder reports "swarm stalled" instead of looping forever (build it with `neighbours: 0`). Run: must fail.
- [X] T012 [US2] Create `bench/sim/model.js` exporting `simulate(settings)`. Settings and defaults: `{ peers: 1000, seeders: 1, neighbours: 64, uplink: 1, seederUplink: 4, latency: 4, groups: 512, window: 32, seed: 1, strategy }`. Rules, all deterministic from `xorshift(seed)`: (1) **Graph**: peers `0..seeders-1` are seeders, the rest downloaders; every peer in random order makes `neighbours` attempts to connect to a random other peer whose degree is below `neighbours`; connections are symmetric. (2) **Peer state**: `has` (bitfield via `bao.createBitfield`), `neighbours`, `availability` (an `Availability` over the groups, counting neighbours), `inflight` (per neighbour, set of group indices), `queue` (FIFO of `{ from, group, readyAt }`), `doneAt`. (3) **Tick loop**, for `t = 0, 1, 2, ...`: first deliver every data arrival due at `t` (if the receiver already holds the group, count it as wasted and discard; otherwise set the bit, and from the next tick tell each neighbour so their `availability.set(group)`); then each peer serves up to its uplink (`seederUplink` for seeders, `uplink` otherwise) requests from its queue whose `readyAt <= t`, each scheduling a data arrival at `t + latency`; then each downloader that is not done pumps: for each neighbour in a per-tick random order, with `window - inflight.size` free slots, build `pool = candidates({ count: groups, has, peerHas: neighbour.has, claimed: any inflight, from: floor(random * groups), limit: SCAN_LIMIT })` using `lib/select.js`, order per the strategy (T013), and send each request as a queue entry at the neighbour with `readyAt = t + latency`. A downloader that holds every group records `doneAt = t` and from then on serves like a seeder. (4) **Stop** when every downloader is done; throw `swarm stalled` if no downloader gained a group for `latency * 4 + 100` consecutive ticks. (5) **Metrics** for the result row: `median` and `last` of `doneAt` over downloaders; `repeatShare` = seeder uploads of a group the seeders (collectively) had already uploaded, divided by all seeder uploads; `wasted` = duplicate arrivals plus rejected requests; `coverage3` = distinct groups among the seeders' first `3 * groups` uploads, divided by `groups`. (6) Import `Availability`, `candidates`, `rank`, `pickFirst`, `SCAN_LIMIT` from `../../lib/select.js` and `bao` from `../../lib/blake3.js`; do not copy any of that logic. `model.js` and `strategies.js` must stay Bare-safe (no `node:` imports, no `process`), because `test/unit/sim.test.js` runs under `npm run test:bare`; only the entry `bench/swarm-sim.js` may use Node APIs. Run T011 (a), (b) and (c)–(e) for the strategies of T013; they pass.

## Implementation strategy

MVP is Phase 3: selection that spreads a crowd, provably and with no benchmark regression; it can ship as 0.3.0 alone. Phase 4 then makes the effect measurable at scale; Phase 5 decides what else is worth building and stops for the user. If T009 shows an existing test depended on file order, change the test, not the behaviour, and say so. If T015 shows the model and the real nodes disagree, stop and fix the model before any verdict is drawn.
